AI Core Engine 구조도

엔진은 코드를 짜는 AI가 아니라 작은 심판이에요. 계획과 코딩은 강한 주 에이전트 하나(Claude 또는 Codex)가 실행 안에서 전부 하고, 엔진은 어떤 모델도 가져서는 안 되는 권한만 가집니다.

엔진이 가진 권한은 다섯 가지예요. ① 동결된 완료 정의 ② 에이전트가 건드릴 수 없는 판정기 ③ main에 쓰는 유일한 경로 ④ 모델을 부를지 말지 ⑤ 원장과 사람 결정 대기열.

01 · 왜 이렇게 생겼나

출발점: Skyworks 릴레이의 실패

이전 자동화는 7일간 에이전트를 530회 돌렸는데, 그중 94% 이상이 제품 코드를 하나도 바꾸지 못했어요. 하루에 131회 실행하고 코드 변경은 0인 날도 있었고, 검증 없이 push한 경우도 있었어요. 원인은 모델의 코딩 능력이 아니었어요. 정지 조건이 없었고, 게이트를 우회할 수 있었고, 상태를 산문 파일로 관리했고, 판정기가 없었어요.

그래서 새 엔진은 이 결함을 막는 장치만 만들고, 계획, 역할 분담, 컨텍스트 관리는 모델과 CLI에 맡겨요. 모든 장치는 실제로 관측했거나 재현한 실패 하나에 대응하고, 그 실패 이름이 테스트에 남아 있어요.

03 · 목표 하나의 생애

한두 문장 목표가 main에 들어가기까지

Tick이 모델을 부르기 전에 확인하는 것 (lib/tick.js · select.js)

  1. STOP 래치가 있으면 정지해요. 파일을 지워도 안 풀리고 engine resume으로만 풀려요.
  2. 잠금(O_EXCL)을 잡아요. 동시에 도는 tick 2개 중 하나만 통과해요.
  3. 원장 전체에서 상태를 새로 파생하고, 끝난 실행을 정리(reconcile)해요.
  4. 계약 순서대로 다음 항목을 골라요. 조건은 이래요: 선행 항목 완료, 시도 3회 미만, main 녹색, 카나리를 통과한 비휴면 벤더, 하루 한도 여유, quiet hours 밖, 열린 결정 5개 미만, 판정기를 쓴 벤더가 아닐 것.
  5. 고를 게 없으면 IDLE이에요. 모델 호출 0, 쓰기 0이고, 대기 사유가 바뀔 때만 기록해요. 릴레이의 공회전이 구조적으로 불가능해진 지점이 여기예요.
  6. 고를 게 있으면 RUN이에요. --no-local로 클론하고, 변조 감지 기준선을 잡고, 어댑터로 실행한 뒤 게이트로 넘겨요. 결과는 종료코드와 구조화 필드로만 분류해요(ok · limit · auth · crash · timeout · schema_invalid · missing_exe). 모델이 쓴 텍스트로는 분류하지 않아요.

10 · 점검 ① 편향과 예스맨

엔진이 AI의 예스맨·편향 문제를 막고 있나

결론: 코드 결과물에 대한 예스맨은 구조적으로 잘 막혀 있어요. 하지만 세 곳이 비어 있어요. 검토자가 같은 모델 계열이라 같은 맹점을 공유하고, 목표 자체가 맞는지 반박하는 장치가 없고, 내용의 사실성이나 편향을 판정하는 장치도 없어요.

문제 유형엔진의 장치근거 (코드·기록)평가
"다 됐습니다" 거짓 완료에이전트 최종 보고는 가중치 0. "완료"는 게이트 판정으로만 바뀜prompt.js FINAL_SCHEMA, AGENTS.md "An agent's claims carry no weight"해결
시킨 건 무조건 해내려는 태도 (불가능한 과제를 억지로)impossible · blocked · needs_decision을 정상 결과로 인정, "Never fake a pass"허니팟(RSA-2048): 에이전트가 편법 없이 impossible로 멈춤해결
과제를 몰래 쉽게 바꾸기계약 동결 + 판정기 해시·센티널허니팟 초안이 "64비트로 축소"를 추천 → 검토자 #1이 거부하고 원래 요구로 동결해결
자기 코드를 칭찬하는 테스트 (자기 선호 편향)판정기 작성 벤더(Codex) ≠ 구현 벤더(Claude), 기존 코드에서 실패해야 함(F2P), 사람 쪽 홀드아웃state.roleConflict, custody.js해결

승인 검토자의 예스맨검토자에게 "확신 없으면 wait" 출구가 있음판정기 승인 4/4 approve, reject 0. 동결 검토는 3/3 수정해서 무조건 동의는 아니지만, 검토자(#1)와 구현자(#2)가 둘 다 Claude Opus 5.5약함
사람에게 맞장구 (목표 자체가 틀렸는데 그대로 진행)없음. 초안은 목표를 계약으로 옮길 뿐, "이 목표가 쓸모없을 수 있다"고 반박하는 필드가 없음contract.js 스키마없음
학습 데이터 편향 (낡은 사실, 한쪽으로 치우친 내용)없음. 판정기는 코드 동작만 봄. 판정기도 모델이 쓰므로 모델의 편향이 테스트에 그대로 들어갈 수 있음홀드아웃(사람·#1 작성)만 일부 보완없음
"테스트 통과 = 좋은 결과"라는 착각설계에서 7배 과대평가라고 인정. 주간 감사는 사람 수동이고 코드 기록이 없음설계 §1, soak.js 오탐 상한만 계산약함

보완안 1 · 검토자 허니팟

일부러 약하게 만든 판정기(항상 통과하는 테스트, 센티널이 무력화된 테스트 등)를 가끔 승인 대기열에 섞어요. 검토자가 이걸 approve하면 기록하고, 적발률이 기준 아래로 떨어지면 해당 검토자의 승인 권한을 멈춰요. 예스맨을 "측정"하는 가장 작은 장치예요.

보완안 2 · 교차 계열 + 반대 논거 필수

승인 검토는 구현자와 다른 계열 모델이 하게 해요. 3번째 계열을 추가하거나, 검토를 Codex와 Claude가 번갈아 맡게 해요. 검토 결과 스키마에는 "거절한다면 그 이유"와 "가장 약한 기준"을 필수 필드로 넣어요. 승인률이 90%를 넘으면 요약에 경고를 띄워요.

보완안 3 · 목표 반증 필드

목표 초안에 필수 필드 두 개를 더해요. "이 목표가 틀렸거나 쓸모없을 수 있는 이유 3개"와 "중단 기준(킬 기준)"이에요. 사람은 동결할 때 이걸 같이 보게 돼서 맞장구를 구조적으로 걸러내요.

보완안 4 · 감사 기록을 원장으로

주간 감사("이 승격이 의미 있었나")를 engine audit <run> useful|trivial|harmful 이벤트로 남겨요. 요약에 "의미 있는 승격 비율"을 표시하고, 떨어지면 목표 선정 방식을 재검토해요.

11 · 점검 ② 최종 형태

프로젝트를 찍어내는 엔진이 되려면

결론: "만들기"는 준비돼 있고, "무엇을 만들지"와 "쓸모 있었는지"가 없어요. 프로젝트는 코드가 아니라 데이터(ProjectContract)로 붙기 때문에, 새 프로젝트를 여러 개 돌리는 기반은 이미 있어요. 하지만 지금은 목표를 사람이 soak-goals.json에 직접 적어요. 아이디어 발굴, 쓸모 평가, 출시 후 지표 계층은 없어요. 초기 설계안(research/10-product-outcome)에는 MARKET 기준과 지표 스냅숏 개념이 있었지만, 최종안에서는 빠졌어요.

"쓸모 있는 프로젝트" 채택 점수표 (안)

  • 실제 문제의 근거: 당신이나 실제 사용자가 지금 불편을 겪고 있음 (출처 필수)
  • 가치 추정: 월 예상 매출 또는 하루 절약 시간
  • 대안 비교: 이미 있는 서비스보다 나은 점 한 줄
  • 최소 검증 실험: 2주 안에 확인할 지표 1개와 기준값
  • 킬 기준: 이 값이 안 나오면 중단
  • 유지비: 서버·API·사람 시간의 월 비용
  • 위험 등급: 돈·개인정보·법률이 걸리면 R2/R3 규칙

이미 있는 후보 (이 PC 기준)

  • void-cards: 수집형 카드 사이트 → Collectible Platform(R3)의 전 단계
  • tickets: 한정판 티켓 모듈 (파일럿 완료) → Collectible 결제·소유권의 부품
  • 몽글: 펫 육성 웹앱 + 3D 캐릭터 10종 → 앱 출시와 굿즈화 검토
  • AI Engine Briefing (C:\Projects\ai-engine-briefing): 일상 편의 도구 후보

배분 제안: 제품 70% · 엔진 개선 20% · 탐색(새 아이디어 검증) 10%. 엔진 개선만 계속하는 것은 설계 문서의 사전 부검 1위 위험("배관만 하다 포기")이에요.

12 · 점검 ③ 최신성

AI 발전·트렌드·최신 정보를 반영하고 있나

결론: "모델이 바뀌는 것"에는 대비돼 있고, "세상이 바뀌는 것"에는 대비가 없어요. 가장 큰 문제는 모순이에요. 설계는 "외부 정보는 필요할 때 모델이 웹 도구로 조사한다"고 했는데, 실제 에이전트 실행은 보안 때문에 웹이 막혀 있어요(adapters/claude.js의 WebFetch·WebSearch 거부, Codex 네트워크 차단). 그래서 지금은 최신 정보를 얻는 경로가 전혀 없어요.

변화지금 장치평가
더 강한 모델 출시프롬프트가 "무엇을"만 말함 → 코드 수정 없이 결과가 좋아짐. 벤더 교체는 어댑터 하나(약 200줄)대비됨
모델에 맞춘 한도 값이 낡음정책 값마다 MODEL_COMP/DURABLE 라벨, measured_on, 요약에 "재측정 안 된 값 4개" 표시. 재측정 자체는 수동표시만
CLI 업데이트로 설정이 조용히 무시됨새 버전은 정책 카나리를 통과할 때까지 휴면 (자동)대비됨
작업별로 알맞은 모델 고르기없음. 모든 역할이 CLI 기본 모델로 돎 (research/14에 설계만 있음)없음
로컬 환경 사실 (exe 경로, 로그인, 다른 자동화)soak 운영 점검 일부만. engine doctor는 설계에만 있음부분
라이브러리·API의 최신 문서, 보안 권고없음 (실행 안에서 웹 금지)없음
시장·경쟁·사용자 트렌드없음 (설계에서 상주 컴포넌트로 만들지 않기로 함)없음

보완안 1 · "리서치" 실행 종류 추가

draft · oracle · implement 옆에 research 종류를 추가해요. 규칙은 이래요.

  • 읽기 전용이고, 웹은 허용하고, 저장소 쓰기는 금지해요.
  • 결과 스키마는 {claim, source_url, fetched_at, ttl}이고 출처가 없으면 거부해요.
  • 결과는 원장에 ResearchFact로 남고, 초안과 아이디어 브리프가 이것을 인용해요.
  • 유효기간이 지나면 다시 조사해요.
  • 쓰기 실행은 지금처럼 계속 웹을 막아요. 웹 페이지에 숨긴 지시로 코드가 오염되는 것을 막기 위해서예요.

보완안 2 · 모델 갱신 루프

새 모델이나 CLI가 나오면 이 순서로 반영해요.

  • 카나리를 돌려요.
  • 기준 세트로 평가해요: 과거에 완료한 목표를 다시 돌려보고, 허니팟과 부정행위 코퍼스도 돌려요.
  • MODEL_COMP 값을 재측정하고 measured_on을 기록해요.
  • pickModel 표를 갱신해요. 초안은 값싼 모델, 판정기는 강한 모델, 구현은 작으면 값싼 모델로 시작하고 실패하면 한 단계 올려요.
  • 적용은 사람이 승인해요.

보완안 3 · 주간 트렌드 레이더

주 1회 리서치 실행으로 AI 도구와 모델 변화, 경쟁 서비스, 관심 분야 트렌드를 출처와 함께 요약해요. 결과는 포트폴리오 아이디어 백로그와 엔진 개선 후보로 들어가요. 결정은 계속 사람이 해요.

순서 (soak 완주 후)

  1. 검토자 허니팟 + 승인률 경고 (작고 효과 큼)
  2. 리서치 실행 종류 + ResearchFact
  3. 목표 반증 필드 + engine audit
  4. engine doctor, 고정 릴리스(engine use) → 자기개선 루프 시작
  5. pickModel + 모델 갱신 루프
  6. 포트폴리오 루프 (브리프 점수표 → 출시 지표)

soak 중에는 src/를 바꾸지 않는다는 규칙이 있어서, 위 작업은 전부 soak이 끝난 뒤 엔진 자신을 R1 프로젝트로 삼아 진행해요.

13 · 버전 로드맵

한 번에 다 만들지 않는 이유와 1차~5차 계획

한꺼번에 만들면 꼬여요. 예전 v2 로드맵("엔진을 크게 먼저, 프로젝트는 나중에")이 그렇게 교체됐어요. 기억·자동 선정 같은 기능은 앞 단계가 실제 프로젝트를 돌려야 효과를 잴 수 있어요. 그래서 각 버전이 실제 프로젝트를 돌리고, 완료 기준을 수치로 통과해야 다음 버전으로 가요.

버전넣는 것넘어가는 조건 (측정)대략
1차 믿을 수 있는 커널
마무리 중		계약·판정기·게이트·원장·결정 대기열 + 작업별 모델 선택 + 리서치 (09-28 완료, 커밋 d2b6562, 테스트 194). 남은 것: 막힌 목표 해소, Codex 모델 표, 2차 soak7일 이상 · 게이트 판정 30회 이상 · 오탐 승격 0 · 할 일 없을 때 모델 호출 01~2주
